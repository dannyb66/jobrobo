# Positioning for staff and principal engineer roles

The resume should read as evidence of system ownership, technical judgment, and leverage—not as a longer list of tools. The target is an engineering leader who can set direction, design durable platforms, raise the quality bar, and still operate at implementation depth.

## Choose a primary market position

Select one primary narrative for each application. A resume can show breadth, but its first half should make one role legible within seconds.

| Position | Emphasize | Representative keywords |
| --- | --- | --- |
| AI platform / infrastructure | Production reliability, inference economics, platform adoption, security, and scale | model serving, inference, GPUs, latency, throughput, autoscaling, AWS, Terraform, Kubernetes, observability, FinOps, SRE |
| Agents / applied AI | Reliable agent systems connected to real workflows | agent runtime, tool calling, orchestration, MCP, context engineering, memory, retrieval, evals, guardrails, human-in-the-loop |
| AI evaluation / safety | Measurable quality, safe deployment, replayability, and governance | evaluation harnesses, golden paths, red teaming, prompt injection, provenance, auditability, policy, regression testing |
| Staff backend / full-stack platform | End-to-end architecture and cross-team delivery | API design, TypeScript, Next.js, Python, data systems, distributed systems, platform engineering, developer experience |
| Founding / generalist technical leader | 0-to-1 execution, product judgment, customer feedback, and durable technical foundations | architecture, roadmap, product discovery, technical strategy, hiring, mentoring, partnerships, go-to-market |

The role profile should influence keyword selection, but it should never cause the resume to claim a technology or responsibility that is not supported.

## The staff/principal evidence formula

Strong bullets usually combine:

```text
scope + architecture decision + constraint + measurable result + organizational leverage
```

For example, a good shape is:

```text
Designed [platform/system] across [scope], choosing [decision] to address [constraint], improving [verified metric] and enabling [teams/users/business outcome].
```

Not every bullet needs all five parts. Across the document, however, show both technical depth and the ability to make other engineers, teams, and systems more effective.

## Summary and headline guidance

The headline should identify the target lane, not every technology:

```text
Staff/Principal Software Engineer | AI Platforms, Agent Systems, and Production Infrastructure
```

A useful summary template for manual editing is:

```text
[Role level] engineer who [owns/designs/leads] [system scope]. Combines [two or three technical strengths] with [leadership/operating strength] to deliver [verified outcomes]. Experienced in [target role vocabulary], with a record of [architecture, scale, reliability, or team leverage evidence].
```

Replace every bracket with evidence from the resume. Avoid generic claims such as “visionary,” “rockstar,” or “AI expert” unless they are backed by concrete scope and outcomes.

## Skills section structure

Use a compact, grouped skills section that reflects the chosen role profile:

```text
AI Systems: agent orchestration, tool calling, retrieval, evaluation, guardrails
Platform: model serving, inference, APIs, distributed systems, observability
Cloud: AWS, Terraform, containers, Kubernetes, CI/CD
Languages: Python, TypeScript, JavaScript, SQL
Leadership: architecture strategy, technical roadmaps, mentoring, cross-functional delivery
```

Put exact job-description terminology first when it is truthful. Expand uncommon acronyms on first use, for example `Model Context Protocol (MCP)`. Keep adjacent skills only when they clarify capability; a 50-item keyword dump weakens prioritization and can push evidence onto a third page.

## Experience bullets: three layers of leverage

Across each major role, aim to show:

1. **System layer:** what was designed, migrated, scaled, or made reliable.
2. **Outcome layer:** the verified impact—latency, cost, reliability, adoption, revenue, quality, or cycle time.
3. **Leverage layer:** how the work changed other teams through standards, APIs, platforms, mentoring, documentation, or roadmap influence.

In `bullets`/`full`, Trek Health can use its dedicated bank, and the named Codex SelfHosted, Sohamhamso, and SponsorSkip entries can use their configured banks. The optimizer inserts selected bank text exactly; other professional experience follows the LLM rewrite path. Review the evidence behind every claim. Marker exclusions and model instructions do not independently establish whether a metric or technology is supported.

## What differentiates principal from staff

The distinction varies by company, so use the job description’s language. In general:

- Staff evidence shows multi-team technical leadership, a durable system outcome, and influence beyond a single project.
- Principal evidence adds organization-level direction, architecture across boundaries, repeated leverage, and decisions that shape a major product or platform area.
- Both levels should show implementation credibility. Strategy without shipped systems is weak evidence; implementation without scope or leverage reads as senior individual contribution.

Useful proof includes architecture reviews, standards adopted by multiple teams, platform usage, migration strategy, incident reduction, hiring or mentoring outcomes, roadmap influence, and cross-functional decisions. Only include the ones the resume can substantiate.

## Two-page allocation

Use the first page to establish the primary position:

- headline and summary;
- compact skills grouped around the target lane;
- strongest recent role with architecture and outcome evidence.

Use the second page for additional experience, entrepreneurial projects, education, and supporting technologies. Preserve whitespace and readable line lengths. The format verifier targets two pages, but the human test is whether a reviewer can find scope, outcomes, and leadership quickly.

## Tailoring workflow

1. Extract the target role’s exact title, systems, responsibilities, and success signals.
2. Select one primary position from the table above.
3. Use `bullets` when Skills and experience/project evidence need alignment, or `skills` for Skills alone. Choose `full` only when its replacement of dated professional-experience titles with the requested title is accurate. The optimizer leaves summaries and project titles unchanged.
4. Review the first page manually before accepting generated text.
5. Keep only keywords supported by the source resume, selected verified bank entries, or clearly equivalent experience.
6. Run the two-page and overflow verifier.
7. Read the final resume as a hiring manager: can the scope, decision quality, outcomes, and leverage be understood without knowing the optimizer?

## Common positioning mistakes

- Listing every AI buzzword instead of explaining one or two production systems deeply.
- Calling a prototype “production” or implying scale that is not documented.
- Replacing architecture outcomes with generic leadership adjectives.
- Using the same summary for infrastructure, applied AI, and founding roles.
- Hiding critical context in a dense skills block while leaving experience bullets vague.
- Letting a model rewrite remove caveats, collaborators, or the actual boundary of responsibility.
